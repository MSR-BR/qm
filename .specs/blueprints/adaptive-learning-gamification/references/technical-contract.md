# Technical contract

## Architecture

Use three layers:

1. **Immutable event ledger:** what verified learning action occurred.
2. **Derived learner state:** concept evidence, due dates, aggregate points, missions, badges, and next action.
3. **Presentation:** Study Journey, assessment, Daily Challenge, simulator, e-mail, and analytics surfaces.

The client may request an action but cannot authoritatively assign XP, mastery, badges, or communication eligibility.

## Canonical event envelope

Every event must contain:

- `event_id` generated by the server or database;
- `user_id` from the verified session;
- `event_type` from a versioned allow-list;
- `occurred_at` and `received_at`;
- `content_id`, `chapter_id`, `section_id`, `concept_ids`, and `source_ids` when applicable;
- `attempt_id` or `activity_id`;
- `idempotency_key` unique for the awardable semantic event;
- `policy_version`;
- evidence metadata with no secrets or unnecessary free text.

Recommended event families:

- `section_completed`;
- `exercise_attempted`, `exercise_corrected`;
- `hint_used`, `solution_revealed`;
- `assessment_started`, `assessment_completed`, `assessment_reviewed`, `assessment_retry_completed`;
- `daily_challenge_completed`;
- `simulator_opened`, `simulator_prediction_recorded`, `simulator_meaningful_interaction`, `simulator_reflection_recorded`, `simulator_goal_completed`;
- `concept_retrieved`, `concept_mastery_reached`;
- `mechanic_eligible`, `mechanic_exposed`, `mechanic_acted`, `mechanic_opted_out`;
- `preference_changed`, recorded outside the reward ledger when appropriate.

## Concept graph and evidence semantics

- Version the reviewed concept/skill graph and prerequisite edges.
- Record problem form or representation so repeated success can span more than one form.
- Keep response evidence capable of representing unaided success, hinted success, solution reveal, low-confidence success, error, and no response.
- Treat slips and guesses as possible measurement noise; do not let one response create or remove mastery.
- Store mechanism-policy versions for game elements so an outcome can be attributed to the delivered configuration.

## Atomicity and idempotency

- Enforce a unique constraint on the idempotency key or the event's natural semantic key.
- Insert the event and update derived projections in one database transaction or security-definer RPC with fixed `search_path` and narrow execution grants.
- Return the existing result for a repeated idempotent request.
- Never insert a reward event and then update the profile in unrelated remote calls.
- Rebuild projections from the ledger when possible.

## Supabase boundaries

- Enable RLS on browser-exposed tables.
- Treat table/function grants and RLS policies as separate controls; verify both.
- Grant browser roles only the operations the product needs and constrain them to `auth.uid()`.
- Keep `service_role` server-side only and grant it the minimum explicit operations required by the server workflow.
- Version schema and grant changes as migrations.
- Test anonymous, authenticated-own-row, authenticated-other-row, admin, and service workflow boundaries.

## Learner profile endpoint

Return a single versioned snapshot with:

- `generated_at` and `policy_version`;
- progress aggregates and evidence freshness;
- points/level and recent reward events;
- concept due/weak summaries without exposing hidden answers;
- assessment, simulator, mission, badge, and next-action state;
- deterministic explanation fields;
- safe empty/insufficient-evidence states.

## Content fidelity

- Use the canonical editorial registry for availability.
- Use the exercise/source manifest for eligible questions and simulator mappings.
- Keep answer keys server-side until feedback is authorized.
- Preserve book notation and render math through the project's safe MathJax pipeline.
- Store generation provenance, model route when used, source identifiers, prompt/policy version, and validation state.

## Analytics separation

Learning events determine learner state. Product analytics measure aggregate behavior. Do not let GA4, telemetry loss, ad attribution, or client-side analytics determine points or mastery.

Maintain separate metrics for learning, behavior, experience, implementation fidelity, and equity/safety. Never relabel clicks, duration, attempts, or point totals as learning gains.
